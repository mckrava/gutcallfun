<objective>
Add a database-only, no-restart infinite replay loop so the product stays alive for
post-World-Cup hackathon judging.

Purpose: once the World Cup ends the fixtures cron discovers no new games and judges see
a dead product. The operator cannot change code or env vars after submission, so the
entire control surface must be a table they can drive with plain SQL.

Output: a `replay_loop` table + entity, and a `ReplayLoopService` cron that clones a
finished replay game forward into a fresh one, forever.
</objective>

<design_constraints>
LOCKED — decided with the user. Do not re-litigate, do not propose alternatives.

**CLONE FORWARD, never reset in place. Delete nothing.** Each iteration INSERTs a new
`game` row rather than resetting the previous one. The verified reasons (confirmed
against current HEAD during planning — do not re-derive):

- No FK in this schema has `ON DELETE CASCADE` (0 hits across `InitialSchema.ts` and
  `initial-request-src/initial-db-structure.sql`). `game_question.trigger_event_id` FKs
  `game_event(id)`, so deleting `game_event` throws once any question exists.
- `ReplayStarterService.wipeAndResetGame` (`replay-starter.service.ts:142`) deletes only
  `game_event`, so re-running an EXISTING replay row is already broken on take 2.
  Clone-forward sidesteps it: a fresh row has zero events, so the wipe is a no-op.
  **DO NOT modify `wipeAndResetGame`.**
- `user_score_profile` / `squad_score_profile` have no `game_id` column and cannot be
  selectively rolled back. Cloning lets points accumulate across iterations — the user
  WANTS judges' points to persist.
- `LiveWindowRegistry.remove()` (`live-window.registry.ts:273`) and
  `GameMutexRegistry.remove()` (`game-mutex.registry.ts:31`) have ZERO callers
  (verified). Reset-in-place would inherit a stale open window + cooldown into the next
  take; a new `game_id` gets fresh registry entries for free.
  **DO NOT add `remove()` calls.**
- Cloning is safe w.r.t. uniqueness: `uq_game_fixture_live` is
  `UNIQUE(fixture_id) WHERE NOT "is_replay"` (`game.entity.ts:8-12`), so many
  `is_replay=true` rows may share one `fixture_id`.
- Replay source resolution is keyed on `fixture_id`
  (`replay-source.service.ts:54-73`): tier A = TxODDS historical by fixtureId, tier B1 =
  `${REPLAY_CAPTURES_DIR ?? cwd()/replay-captures}/<fixtureId>.ndjson`, tier B2 = the
  game's own `game_event` rows. A clone carrying the same `fixture_id` resolves the
  identical A/B1 source. B2 is single-use by construction and irrelevant here.

**Hard scope limits:**
- Backend only (`apps/gutcallfun-core`). DO NOT touch `apps/gutcallfun-ui`.
- DO NOT change the LOCKED points ladder (5/7/15/100), question timing constants, or any
  live-engine logic.
- DO NOT add an env var for the toggle. DB only — that is the entire point.
- DO NOT seed or enable a loop row in the migration. Ship the feature disabled.
- DO NOT expose `replay_loop` via any REST controller, DTO, or WS payload.
</design_constraints>

`SourceSchedulerService`. Constructor injects four repositories via `@InjectRepository`:

Decorate the tick with `@Cron('*/30 * * * * *')` (6-field, seconds granularity — the same
form `SourceSchedulerService` uses). `ScheduleModule.forRoot()` already exists in
`ingest.module.ts:12` — DO NOT add a second one.

TICK BODY. The handler must NEVER throw, so guard everything:

1. Inside a try/catch, `loopRepo.find({ where: { enabled: true } })`. On a thrown error,
   log and return — there is nowhere to persist it.
2. If the result is empty, return immediately. This is the off-state hot path: one
   indexed read (served by `idx_replay_loop_enabled`) and nothing else.
3. For each row, run `processRow(row)` inside its own try/catch so one bad row cannot
   stop the others.
   - On success, if `row.lastError` was non-null, clear it (`lastError: null`) along with
     `updatedAt: new Date()`.
   - On failure, persist the message to `last_error` truncated to 500 chars, plus
     `updatedAt: new Date()`, and log at error level. Wrap that persistence write in its
     own `.catch()` so a DB failure while recording a failure still cannot escape.

processRow(row) LOGIC, in this order:

a) Load the current game: `row.currentGameId` non-null -> `gameRepo.findOne({ where: { id:
   row.currentGameId } })`, else null.

b) STALL WATCHDOG — runs BEFORE the advance check. If the current game exists and its
   status is `GameStatus.LIVE`:
   - Find the newest event:
     `gameEventRepo.findOne({ where: { gameId }, order: { receivedAt: 'DESC' } })`.
   - Compute lastActivity as `latest?.receivedAt ?? game.updatedAt ?? game.startsAt ??
     game.createdAt`. `createdAt` is NOT NULL, so this chain always terminates with a
     real Date — never compare against null.
   - If `now - lastActivity > row.stallTimeoutSeconds * 1000`, force the game finished
     using the conditional-claim query-builder pattern that
     `game-finalisation.service.ts` and `source-scheduler.service.ts:63-69` already use:
     `.update(GameEntity).set({ status: GameStatus.FINISHED, updatedAt: new Date() })
      .where('id = :id', ...).andWhere('status = :live', { live: GameStatus.LIVE })`.
     The `andWhere` guard means a real `game_finalised` landing concurrently wins and
     this becomes a 0-row no-op. Log the forced finish. Then RETURN — the next tick
     performs the advance, which also lets `restart_delay_seconds` apply cleanly.
   - If it is live and fresh, RETURN (no-op).

   Document the three real failure modes this covers, since none are hypothetical:
   (i) `SourceSchedulerService.startGame` claims `scheduled -> live` BEFORE calling
   `start()` and never rolls the status back if the start throws
   (`source-scheduler.service.ts:63-102`), stranding the row live forever;
   (ii) finalisation keys on the `game_finalised` ACTION
   (`game-finalisation.service.ts:57`), so a replay source whose tail lacks that action
   never reaches finished; (iii) a crash mid-replay — boot recovery deliberately rebuilds
   in-memory state but does not resume a replay source
   (`game-state-rebuild.service.ts:101-105`), which is the open pending todo
   `replay-restart-orphans-mid-flight-game`. All three present identically as
   status=live + no new events for N seconds.

c) ADVANCE. Reached only when the current game is null, FINISHED, or CANCELLED.
   Gate on both, returning early if either fails:
   - delay: `row.lastRestartAt` is non-null AND
     `now - lastRestartAt < row.restartDelaySeconds * 1000` -> return.
   - cap: `row.maxIterations` is non-null AND
     `row.iterationsRun >= row.maxIterations` -> return. (null = unlimited.)

   Then clone. Resolve the display-identity source as
   `template = row.templateGameId ? findOne(templateGameId) : null`, then
   `source = template ?? currentGame` (fall back to the previous iteration's row when no
   template is configured). Build with `gameRepo.create({...})` + `gameRepo.save(row)` —
   the same insert convention `fixtures-cron.service.ts:90-102` uses.

   New row fields:
   - `fixtureId: row.fixtureId` (NOT the source's — the loop row is authoritative, and
     this is what makes the clone resolve the same replay source)
   - `isReplay: true`, `status: GameStatus.SCHEDULED`, `startsAt: new Date()`
   - copied from `source` (each `?? null`, or `?? true` for the boolean):
     team1Name, team2Name, competition, participant1Id, participant2Id,
     participant1IsHome, team1JerseyColor, team2JerseyColor.
     The request names only team1_name/team2_name/competition; the participant ids and
     jersey colours are copied too because they are the same display-identity set and the
     UI renders from them — a clone missing them would show judges an unstyled, unnamed
     match. Note this superset in a code comment.
   - explicitly zeroed/nulled fresh state: `scoreP1: 0`, `scoreP2: 0`,
     `currentStatusId: null`, `streamCursor: null`, `streamCursorAt: null`.

   Then carry participation forward, but only when `row.currentGameId` is non-null (there
   is no previous game on iteration 1):
   - `userGameRepo.find({ where: { gameId: row.currentGameId } })`
   - if that result is non-empty, insert via the query builder:
     `.insert().into(UserGameEntity).values(prev.map(r => ({ gameId: newGame.id, userId:
      r.userId, squadId: r.squadId }))).orIgnore().execute()`.
     `orIgnore()` emits `ON CONFLICT DO NOTHING`, matching the composite PK
     `(game_id, user_id)`. `squadId` is preserved. Skip the insert entirely on an empty
     array — TypeORM throws on an empty `values()`.

   Finally update the loop row: `currentGameId: newGame.id`,
   `lastRestartAt: new Date()`, `iterationsRun: row.iterationsRun + 1`,
   `lastError: null`, `updatedAt: new Date()`. A plain incremented value (rather than a
   SQL expression) is correct and testable here because the deployment shape is a single
   long-lived process with one cron instance.

   Log the clone at `log` level with old game id, new game id, and iteration count.

DO NOT call `ReplayStarterService` or `StreamManagerService` from this service. Inserting
`status='scheduled'` with `starts_at=now()` is the entire handoff:
`SourceSchedulerService` (@Cron */15s) claims it on its next tick and dispatches the

State this explicitly in the file header.
