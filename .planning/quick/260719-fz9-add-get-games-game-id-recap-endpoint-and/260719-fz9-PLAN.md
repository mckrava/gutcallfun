## Facts established during planning — do not re-derive

- `game_event.payload` stores the FULL raw feed message, and the feed wraps its
  body as `{ Update: {...} }` on some messages. Every read of the payload must
  use the codebase's existing convention `inner = raw.Update ?? raw`
  (`message-normalizer.ts:178`, `possession.ts`, `goals.ts`). A bare
  `payload->'Clock'` read misses the wrapped half of the corpus.
- The four possession stage values in `game_event.type` are exactly
  `safe_possession`, `attack_possession`, `danger_possession`,

3. Calls + `me` aggregates, one query scoped to the caller:

Order by `COALESCE(ge.feed_ts, uga.created_at) ASC`.
   The LEFT JOIN on `game_event` is load-bearing: `trigger_event_id` is nullable and an inner join would silently drop those calls from the recap entirely.
   Derive in TS from these rows: `answered` = row count; `resolved` = rows with non-null awarded_points; `total_points` = sum of awarded_points; `exact` = rows where picked_outcome equals actual_outcome; `voided` = rows whose state is 'voided'; `hit_rate` = successful_outcome-true count divided by `resolved`, or 0 when resolved is 0; `best_call` = the resolved row with the highest awarded_points (earliest minute breaks ties), or null when nothing scored above 0.
   Do NOT join `game_question_outcome` — `ladder_delta` / adjacent-vs-exact is out of scope; `MatchEkg` colours green/red from `successful_outcome` alone.
