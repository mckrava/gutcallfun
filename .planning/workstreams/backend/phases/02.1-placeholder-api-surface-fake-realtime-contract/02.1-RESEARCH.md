## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01: Realistic shaped mocks, NOT empty 200s.** Every endpoint returns a correctly-typed
  DTO populated with realistic fake data whose field names and types match
  `initial-db-structure.sql` exactly.
- **D-02: No auth in this phase.** No JWT, no session, no guard. `user_id` is passed
  explicitly as a path/query/body parameter wherever it is needed. **ACCEPTED COST:** every
  endpoint signature carrying a `userId` parameter WILL change when Phase 3 lands. Do not
  silently add an auth stub.
- **D-03: WebSocket emits a full fake cycle, not just a heartbeat.** On subscribe: a full
  `snapshot`. Then, looping: a `game_event` every ~4s, a `question` every ~30s carrying 4
  options with `expires_at = now + 5s`, and ~5s later its `resolution` (winning option +
  awarded points).
- **D-04: Mock data must be deterministic.** No per-request `Math.random()`. The same request
  returns the same body. Time-derived fields like `expires_at` are the deliberate exception.
- **D-05: Contract frozen here, implementations owned later.** Phase 5 must be able to swap
  real logic in behind these exact DTOs with zero UI rework. Treat the DTO shapes as the
  deliverable, the mock bodies as scaffolding.

## Summary

This is a brownfield insertion phase into a codebase where Phases 1-2 built **only** the data
layer and the TxLINE ingest pipeline — confirmed by direct source inspection, there is
currently **zero** REST or WebSocket surface, no Swagger, no global `ValidationPipe`, and no
CORS configuration anywhere in `apps/gutcallfun-core/src`. `@nestjs/websockets`,
`@nestjs/platform-socket.io`, `socket.io`, `socket.io-client`, and `@nestjs/swagger` are all
absent from `package.json` and must be added. This means the planner is not "extending" an
existing API surface — it is building the entire REST + WS layer from scratch, but must do so
inside the strong architectural conventions Phase 1/2 already established (feature-folder
modules under `src/modules/`, camelCase TypeORM entities with explicit `name:` snake_case
column mapping, `ConfigService`-injected env access, fail-fast `AppConfig` validation via
`class-validator`/`plainToInstance`).

The single highest-value resolution this research makes is the **field-casing decision**:
TypeORM entities are camelCase (`gameId`, `startsAt`), but CONTEXT.md D-01 requires the wire
contract to match `initial-db-structure.sql` (snake_case) exactly. The recommendation is to
declare DTO class properties **literally in snake_case** (`game_id`, `starts_at`) for both
request and response bodies — verified lint-safe (no `camelCase` ESLint rule is configured) —
rather than adding `@Expose`/`@Transform` indirection. Entities keep their existing camelCase
convention untouched; DTOs are a separate, hand-constructed translation boundary, populated
directly from fixture constants in this phase and by explicit entity→DTO mapper functions in
Phase 5.

The second highest-value resolution is the **fake-cycle vs. real-ingest collision question**
CONTEXT.md flagged as open: because no gateway or WS broadcaster exists anywhere in the
codebase yet, there is **no runtime collision risk today** — the ingest pipeline has zero WS
awareness. The risk is purely forward-looking (Phase 5 wiring real broadcasts into the same
event names). The mitigation is architectural isolation: build the fake-cycle module with zero
imports from `IngestModule`/`StreamModule`, name it unambiguously as mock-scoped, and leave an
explicit deletion marker so Phase 5 can remove it wholesale.

**Primary recommendation:** add `@nestjs/websockets` + `@nestjs/platform-socket.io` +
`socket.io` (runtime) and `socket.io-client` (dev, for gateway e2e tests) at version
`11.1.28`/`4.8.3` (exact match to the already-pinned `@nestjs/core@11.1.28`), add
`@nestjs/swagger@11.4.6`; build REST resources under `src/modules/api/<resource>/` and the
gateway under `src/modules/realtime/`; store all mock fixture data in one `src/mocks/fixtures/`
directory (file-per-entity, single barrel) to keep D-04 determinism auditable in one place;
use `SchedulerRegistry` from the already-installed `@nestjs/schedule` for named, introspectable
per-room fake-cycle timers instead of a hand-rolled `Map<string, Timeout[]>`.

## Codebase Discovery (Current State — Verified 2026-07-18)

Direct inspection of `apps/gutcallfun-core/src` and `package.json`, answering the discovery
questions from the phase brief:

1. **No socket.io gateway exists.** `grep -r "@WebSocketGateway\|@nestjs/websockets\|@nestjs/platform-socket.io"` across `src/` returns nothing. `package.json` has no `@nestjs/websockets`, `@nestjs/platform-socket.io`, `socket.io`, or `socket.io-client` in either `dependencies` or `devDependencies`. **All must be added.**
2. **`main.ts` bootstrap is minimal** (`src/main.ts`, 9 lines):
   ```ts
   const app = await NestFactory.create(AppModule);
   app.enableShutdownHooks();
   await app.listen(process.env.PORT ?? 3000);
   ```
   No `SwaggerModule`/`DocumentBuilder`, no `app.useGlobalPipes(new ValidationPipe(...))`, no
   `app.enableCors()`, no global prefix. `enableShutdownHooks()` **is** active (Phase 1
   delivered it) — relevant to the timer-cleanup pitfall below.
3. **Existing module/file conventions** (from `src/modules/ingest/**`): one feature folder per
   concern (`fixtures/`, `stream/`, `replay/`, `recovery/`, `state/`, `persistence/`, `events/`),
   each with its own `*.module.ts` aggregated into a parent `ingest.module.ts`; services are
   `*.service.ts` (`FixturesCronService`, `EventIngestService`); no barrel `index.ts` files
   anywhere in `src/models` or `src/modules`; config is read via `ConfigService` injected from
   `@nestjs/config` (`private readonly config: ConfigService`, `.get<T>('KEY')`) — **not** a
   custom `AppConfig.getInstance()` singleton class as CLAUDE.md's stack doc speculated; the
   actual Phase 1 implementation uses NestJS's own `ConfigModule.forRoot({ isGlobal: true,
   validate })` + `ConfigService` DI, which is the correct pattern to keep matching. `@Cron`
   from `@nestjs/schedule` is used directly on service methods (`FixturesCronService`).
4. **Entity ↔ DTO casing tension is real and confirmed.** All 12 entities in `src/models/**`
   use camelCase TS properties with `@Column({ name: 'snake_case_column' })` explicit mapping
   (e.g. `GameEntity.fixtureId` ↔ column `fixture_id`). TypeORM's default `find()`/`save()`
   returns camelCase-keyed objects. **Resolution: see Architecture Patterns > Field Casing.**
5. **No existing controllers/DTOs.** `AppController`/`AppService` are the untouched Nest
   boilerplate ("Hello World"). There is no REST convention to inherit — this phase establishes
   it from scratch, and should follow the ingest module's feature-folder pattern rather than
   inventing a new one.
6. **Test conventions:** unit specs are colocated (`*.spec.ts` next to the file under test,
   e.g. `fixtures-cron.service.spec.ts`); e2e specs live in `test/*.e2e-spec.ts` using
   `Test.createTestingModule({ imports: [AppModule] })` + `supertest` against
   `app.getHttpServer()` (see `test/app.e2e-spec.ts`). Jest config: unit tests run from
   `rootDir: "src"` with `testRegex: ".*\\.spec\\.ts$"`; e2e uses a separate
   `test/jest-e2e.json` (`testRegex: ".e2e-spec.ts$"`). `socket.io-client` is **not** currently
   a devDependency — must be added for any gateway e2e test that connects a real client. A
   **pre-existing, documented open issue** (`.planning/todos/pending/stream-abort-unhandled-rejection-and-e2e-open-handles.md`)
   already flags that `npm run test:e2e` needs `--forceExit` because something (suspected:
   `@nestjs/schedule` cron timers) doesn't tear down cleanly — **naive `setInterval` timers in
   the new gateway will make this measurably worse** unless the cleanup pattern in Architecture
   Patterns > Timer Lifecycle is followed exactly.

### Pattern 1: Field Casing — snake_case DTOs, camelCase entities

**What:** DTO classes (both request and response, REST and WS) declare their TypeScript
property names literally in `snake_case`, matching `initial-db-structure.sql` column names
1:1. Example:
```typescript
// src/modules/api/games/dto/game-response.dto.ts
import { ApiProperty } from '@nestjs/swagger';

export class GameResponseDto {
  @ApiProperty({ example: 42 })
  id: number;

  @ApiProperty({ example: 'live', enum: ['scheduled', 'live', 'finished', 'cancelled'] })
  status: string;

  @ApiProperty({ example: '2026-07-18T15:00:00.000Z', nullable: true })
  starts_at: string | null;

  @ApiProperty({ example: 'Brazil' })
  team1_name: string | null;

  @ApiProperty({ example: 'Argentina' })
  team2_name: string | null;

  @ApiProperty({ example: 1 })
  score_p1: number;

  @ApiProperty({ example: 0 })
  score_p2: number;

  @ApiProperty({ example: false })
  is_replay: boolean;
}
```
**When to use:** every DTO in `src/modules/api/**/dto` and `src/modules/realtime/dto`.

**Why (resolving the tension CONTEXT.md flagged):** D-01 requires the wire contract to match
`initial-db-structure.sql` field names exactly; the existing 12 TypeORM entities are camelCase
by established Phase-1 convention (`@Column({ name: 'starts_at' }) startsAt: Date`) and that
convention should **not** change (would touch Phase 1/2 files, risking regression of the green
148-unit/2-e2e suite — explicitly forbidden). The cleanest boundary is: entities own the
DB-facing camelCase shape, DTOs own the wire-facing snake_case shape, and the two are never the
same class. This phase constructs DTOs directly from fixture constants (no entity in the loop
at all), so there is no mapping code to write yet — but the convention is what makes Phase 5's
job "swap the internals, freeze the DTOs" actually cheap: Phase 5 adds one small
`toGameResponseDto(entity: GameEntity): GameResponseDto` mapper per resource, nothing else
changes.

**Verified lint-safe:** `apps/gutcallfun-core/eslint.config.mjs` has no `camelCase`/naming-convention rule (checked directly — only `no-explicit-any`, `no-floating-promises`, `no-unsafe-argument`, and prettier are configured), so `snake_case` DTO properties will not trigger lint failures.

**Apply the same convention to request DTOs and query params, and to the WS message envelope
fields**, for one consistent contract in both directions (e.g. `POST /answers` body:
`{ user_id, game_question_id, selected_option_id }`, not the camelCase shown in CONTEXT.md's
illustrative example — that route-map sketch predates this resolution).

### Pattern 3: WS Gateway with Timer Lifecycle (avoids the known open-handles pitfall)

**What:** a gateway that joins clients to per-game rooms, sends an immediate `snapshot`, and
starts a room-scoped fake cycle using `SchedulerRegistry` for named, cleanly-torn-down
intervals.
```typescript
// src/modules/realtime/realtime.gateway.ts
import {
  WebSocketGateway, WebSocketServer, SubscribeMessage,
  OnGatewayDisconnect, MessageBody, ConnectedSocket,
} from '@nestjs/websockets';
import { Server, Socket } from 'socket.io';
import { FakeCycleService } from './fake-cycle.service';
import { buildSnapshot } from '../../mocks/fixtures/games.fixtures';

@WebSocketGateway({ cors: false }) // cors resolved from ConfigService — see Pattern 4
export class RealtimeGateway implements OnGatewayDisconnect {
  @WebSocketServer() server: Server;

  constructor(private readonly fakeCycle: FakeCycleService) {}

  @SubscribeMessage('subscribe')
  handleSubscribe(
    @MessageBody() body: { game_id: number },
    @ConnectedSocket() client: Socket,
  ): void {
    const room = `game:${body.game_id}`;
    void client.join(room);
    client.emit('snapshot', buildSnapshot(body.game_id));
    this.fakeCycle.startCycleForRoom(room, body.game_id, this.server);
  }

  handleDisconnect(client: Socket): void {
    for (const room of client.rooms) {
      const size = this.server.sockets.adapter.rooms.get(room)?.size ?? 0;
      if (room.startsWith('game:') && size <= 1) {
        // this client is the last one in the room (size includes itself pre-leave)
        this.fakeCycle.stopCycleForRoom(room);
      }
    }
  }
}
```
```typescript
// src/modules/realtime/fake-cycle.service.ts
import { Injectable, OnModuleDestroy } from '@nestjs/common';
import { SchedulerRegistry } from '@nestjs/schedule';
import { Server } from 'socket.io';
import { buildGameEvent, buildQuestion, buildResolution } from '../../mocks/fixtures/game-events.fixtures';

@Injectable()
export class FakeCycleService implements OnModuleDestroy {
  constructor(private readonly scheduler: SchedulerRegistry) {}

  startCycleForRoom(room: string, gameId: number, server: Server): void {
    const heartbeatName = `heartbeat:${room}`;
    if (this.scheduler.doesExist('interval', heartbeatName)) return; // already running

    const heartbeat = setInterval(() => server.to(room).emit('game_event', buildGameEvent(gameId)), 4_000);
    heartbeat.unref?.();
    this.scheduler.addInterval(heartbeatName, heartbeat);

    const questionCycleName = `question-cycle:${room}`;
    const questionCycle = setInterval(() => this.runQuestionCycle(room, gameId, server), 30_000);
    questionCycle.unref?.();
    this.scheduler.addInterval(questionCycleName, questionCycle);
  }

  stopCycleForRoom(room: string): void {
    for (const name of [`heartbeat:${room}`, `question-cycle:${room}`]) {
      if (this.scheduler.doesExist('interval', name)) {
        this.scheduler.deleteInterval(name);
      }
    }
  }

  private runQuestionCycle(room: string, gameId: number, server: Server): void {
    server.to(room).emit('question', buildQuestion(gameId));
    const resolutionTimer = setTimeout(
      () => server.to(room).emit('resolution', buildResolution(gameId)),
      5_000,
    );
    resolutionTimer.unref?.();
  }

  // Belt-and-suspenders: SchedulerRegistry intervals are NOT auto-cleared by
  // Nest on shutdown (verified: intervals added via addInterval persist
  // until deleteInterval is called explicitly) — this hook guarantees no
  // interval outlives app.close(), which is what test:e2e relies on and
  // what the pre-existing open-handles issue is about.
  onModuleDestroy(): void {
    for (const name of this.scheduler.getIntervals()) {
      this.scheduler.deleteInterval(name);
    }
  }
}
```
**When to use:** this exact pattern for the fake cycle. The `.unref()` calls matter for two
independent reasons: (1) they let the Node process exit even if `onModuleDestroy` cleanup is
somehow skipped, directly mitigating the documented open-handles issue; (2) they do **not**
affect production behavior, since the long-lived HTTP/WS server keeps the event loop alive
regardless — `.unref()` only opts a *specific* timer out of counting toward "is anything keeping
the process alive," it does not stop the timer from firing.

### Pattern 5: Pagination (resolves the open question)

- **`GET /games/:gameId/events`** — use a **seq-cursor**, not limit/offset:
  `?after_seq=<int>&limit=<int>`, response `{ items: GameEventResponseDto[], next_seq: number | null }`.
  Rationale: `game_event.seq` is the table's actual monotonic ordering key
  (`UNIQUE(game_id, seq)`, `idx_ge_type`/`idx_ge_action_id` both keyed off `game_id`), the table
  is append-only and can grow large over a match, and offset pagination degrades and can skip/
  duplicate rows under concurrent inserts on a live-growing log — a well-documented anti-pattern
  for exactly this access shape. This is also what Phase 5 will need to implement for real, so
  choosing it now avoids a breaking pagination-shape change later.
- **`GET /games`, `GET /leaderboard`** — plain `?limit=<int>&offset=<int>` is fine; these are
  bounded, not append-only-log-shaped resources, and CONTEXT.md's route map already writes
  `?limit=` for the leaderboard.

### Pattern 6: WS Contract Documentation (Swagger cannot describe WS — resolves the open question)

**What:** OpenAPI/Swagger has no native WebSocket support [CITED: cross-referenced via
websearch against nestjs/nest#1794 "Websocket event's swagger support", still open/unresolved
upstream]. Two real options exist: (a) `nestjs-asyncapi`, a third-party decorator-based AsyncAPI
doc generator modeled on `@nestjs/swagger`'s API; (b) hand-written markdown. **Recommendation:
(b) for this phase.** Concretely:
1. Every WS message DTO (`SnapshotDto`, `GameEventMessageDto`, `QuestionMessageDto`,
   `ResolutionMessageDto`, `VoidMessageDto`) is a real class decorated with `@ApiProperty`
   exactly like REST DTOs (same snake_case convention).
2. Register them in the Swagger schema section even though no REST route references them,
   using `@ApiExtraModels(SnapshotDto, GameEventMessageDto, QuestionMessageDto, ResolutionMessageDto, VoidMessageDto)`
   on any controller (or a tiny no-op controller dedicated to this) — this makes the shapes
   browsable in Swagger UI's schema list, even without a "try it" button for WS.
3. Write a short `docs/WS-CONTRACT.md` (or a `## WebSocket Contract` section appended to the
   Swagger description) listing: connection URL, the `subscribe` client→server event and its
   payload shape, and the four server→client event names with a one-line description each and
   a link/reference to the corresponding DTO class name shown in Swagger's schema section.

**Why not `nestjs-asyncapi`:** it is a real, actively-referenced package for this exact problem,
but introduces a new documentation paradigm, a new dependency, and its own bootstrap wiring —
not worth the setup/verification cost inside a same-day feature-freeze window when the DTO
classes + one markdown file achieve the stated goal ("UI developer can build every screen
without inventing a single field name") at a fraction of the cost. Revisit post-hackathon if the
WS contract grows past 5 event types.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Deterministic mock data | A seeded PRNG (e.g. hand-rolled `mulberry32` keyed by request params) | Static fixture constants in `src/mocks/fixtures/*.ts` | D-04 requires zero per-request randomness; a PRNG adds a dependency-free but still nontrivial "derive the same seed from the same request" problem for no benefit when the entity count is small (a handful of demo games/users/questions) — literal constants are simpler and trivially auditable |
| Request validation / 4xx shaping | Manual `if (!body.x) throw new BadRequestException(...)` guards per field | `class-validator` DTOs + global `ValidationPipe({ whitelist, transform, forbidNonWhitelisted })` | Already a mandatory peer of `@nestjs/swagger`; one validation library serves both DTO validation and (existing) env validation; hand-rolled guards can't be introspected by Swagger the way decorated DTOs can |
| Per-room timer bookkeeping | A bespoke `Map<string, NodeJS.Timeout[]>` registry with manual start/stop logic | `SchedulerRegistry` (`@nestjs/schedule`, already installed) `addInterval`/`deleteInterval`/`getIntervals`/`doesExist` | Named, introspectable, and matches the one dynamic-scheduling convention already in the codebase (`FixturesCronService`'s `@Cron`); reduces the surface area for the exact kind of leaked-timer bug the pre-existing open-handles issue already documents |
| OpenAPI schema generation | Hand-written JSON/YAML OpenAPI spec files | `@nestjs/swagger` decorators (`@ApiProperty`, `DocumentBuilder`) | Locked stack choice (API-01); decorator-driven docs stay in sync with the DTOs automatically, hand-written specs drift immediately |
| WS event documentation | `nestjs-asyncapi` full toolchain | Hand-written `WS-CONTRACT.md` + `@ApiExtraModels`-registered DTOs | See Pattern 6 — right tool for a larger project, overkill for a same-day 5-event-type contract |
| Response field-casing conversion | `class-transformer` `@Expose({name})` + global `ClassSerializerInterceptor` | Literal snake_case DTO property names | See Pattern 1 — avoids interceptor indirection and the "raw entity accidentally serialized wrong" foot-gun for a phase with no entity-to-DTO mapping code yet anyway |

**Key insight:** every "don't hand-roll" item above already has its correct tool sitting in
`package.json` or the CLAUDE.md-locked stack — the risk in this phase isn't reaching for an
unknown library, it's reaching for ad-hoc code where an already-adopted tool does the job better
(`SchedulerRegistry` over a raw `Map`, `class-validator` over manual guards).

## Common Pitfalls

### Pitfall 1: Jest open handles get worse, not better
**What goes wrong:** the new gateway's per-room `setInterval`s keep the Jest worker process
alive after `app.close()`, on top of the pre-existing (documented, unfixed) issue where
`test:e2e` already needs `--forceExit`.
**Why it happens:** `app.close()` triggers `onModuleDestroy()`/`onApplicationShutdown()` but
does **not** automatically clear timers a provider created — cleanup is the provider's job.
[CITED: nestjs.com lifecycle-events doc, cross-referenced via websearch]
**How to avoid:** follow Pattern 3 exactly — `SchedulerRegistry` + `onModuleDestroy` clearing
every registered interval, plus `.unref()` as a second line of defense.
**Warning signs:** `npm run test:e2e` hangs longer than before this phase, or Jest reports a
growing "open handles" list that now includes `Timeout` objects pointing at
`fake-cycle.service.ts`.

### Pitfall 2: CORS "works" on REST but the WS handshake still fails
**What goes wrong:** `app.enableCors()` is added, REST calls succeed from the Next.js origin,
but the socket.io client gets a CORS error on the handshake and the UI dev reports "WS doesn't
connect."
**Why it happens:** socket.io's handshake is a separate HTTP upgrade path that NestJS's
`enableCors()` does not cover — this is a well-documented, still-open confusion point.
[CITED: docs.nestjs.com/websockets/gateways, nestjs/nest#7649]
**How to avoid:** Pattern 4 — configure `cors` on the `@WebSocketGateway()` decorator
explicitly, using the same validated `WEB_APP_ORIGIN` value.
**Warning signs:** browser devtools shows a CORS preflight failure specifically on the
`socket.io/?EIO=4&transport=polling` (or websocket upgrade) request, while `/api-docs` and
other REST routes work fine from the same origin.

### Pitfall 3: A raw entity accidentally leaks camelCase JSON, violating D-01
**What goes wrong:** a controller method returns a TypeORM entity instance (or an object
literal with entity-style camelCase keys) instead of a DTO instance; Nest's default JSON
serializer emits it as-is, producing `{"gameId": 42, "startsAt": "..."}` instead of the
contracted `{"game_id": 42, "starts_at": "..."}`, silently breaking the frozen contract for
whichever screen binds to that field.
**Why it happens:** nothing enforces the DTO boundary automatically in this phase (no
`ClassSerializerInterceptor`, deliberately — see Pattern 1); it's a discipline problem, not a
framework one.
**How to avoid:** every controller method's return type must be the DTO class (or
`DTO | DTO[]`), never `any`/entity types; since fixtures are constructed directly as DTO
literals in `src/mocks/fixtures/*.ts` this phase, there's no entity anywhere in the call path
to accidentally leak — but flag this explicitly for Phase 5, where entities *will* be in the
call path and the mapper function becomes load-bearing.
**Warning signs:** a Swagger-documented field name (snake_case) doesn't match what the actual
HTTP response body contains (camelCase) — catch this with a quick e2e assertion per endpoint
(see Validation Architecture note below).

### Pitfall 4: `squad.id` has no database default — mocks must not imply auto-generation
**What goes wrong:** `initial-db-structure.sql` declares `squad.id` as `int NOT NULL PRIMARY
KEY` with **no** `GENERATED ALWAYS AS IDENTITY` and no `DEFAULT` (unlike `game.id`, which is
`GENERATED ALWAYS AS IDENTITY`). If the mock `POST /squads` implementation (or, later, the
Phase-5 real one) assumes Postgres will auto-assign an id the way it does for `game`, inserts
will fail or silently collide.
**Why it happens:** easy to miss — `SquadEntity` correctly uses `@PrimaryColumn` (not
`@PrimaryGeneratedColumn`), confirmed by direct inspection of
`src/models/squad/squad.entity.ts`, but the SQL comment doesn't call out this asymmetry vs.
`game.id` explicitly.
**How to avoid:** for this phase's mock `POST /squads`, assign an id deterministically from an
in-memory fixture counter (e.g. `Math.max(...existingIds) + 1`, still deterministic per D-04
since fixture state is fixed) and return it in the response DTO. **Flag explicitly for the
Phase 5 planner:** real squad creation needs an app-level id-assignment strategy (e.g. a
Postgres sequence created in a migration, or a `MAX(id)+1` query with a unique-constraint retry
loop) — this is out of scope for 02.1 but must not be silently assumed away.
**Warning signs:** none visible in this phase (mocks control their own ids) — this is a
forward-looking flag only.

### Pitfall 5: Nested DTO validation silently no-ops without `@Type()`
**What goes wrong:** `game_question_option[]` embedded in the `game_question` response (or any
future nested-array request DTO) needs `@ValidateNested({ each: true })` **and**
`@Type(() => GameQuestionOptionDto)` from `class-transformer` together — omitting `@Type()`
means `class-validator` validates the raw plain object instead of an instance of the nested
DTO class, and decorator-based rules on the nested class are silently skipped.
**Why it happens:** well-known `class-validator`/`class-transformer` gotcha, easy to miss under
time pressure since the endpoint will still "work" (no validation error is thrown) — it just
validates nothing on the nested shape.
**How to avoid:** for any DTO with a nested array/object property, always pair
`@ValidateNested({ each: true })` with `@Type(() => NestedDto)`.
**Warning signs:** a malformed nested payload (e.g. a `game_question_option` missing
`base_gain`) is accepted with 200/201 instead of rejected with 400.
