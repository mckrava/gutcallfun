# Phase 2.1: Placeholder API Surface & Fake Realtime Contract - Context

**Gathered:** 2026-07-18
**Status:** Ready for planning
**Source of truth:** `initial-request-src/api-mockup.md` (user request, 2026-07-18) + decisions captured below

<domain>
## Phase Boundary

Freeze the complete client-facing contract — REST endpoints and the socket.io event
stream — and serve it with realistic mock data, so the UI developer can build and
integrate every screen immediately instead of waiting on Phases 3–5.

**Includes:** all REST endpoints listed below returning HTTP 200 with correctly-typed,
schema-faithful, non-empty mock payloads; Swagger documentation; class-validator DTOs;
CORS; a socket.io gateway emitting a looping fake game cycle (snapshot → game_event
heartbeat → question → resolution).

**Excludes:** real persistence behind these endpoints, real auth (Phase 3), real window
opening/resolution logic (Phase 4), real WS wiring to the live state machine (Phase 5).
This phase writes the *contract*; Phase 5 swaps implementations in behind identical DTOs.

**Must not touch:** the Phase 2 ingest pipeline (`src/modules/ingest/**`). Its suite —
148 unit + 2 e2e — must stay green.
</domain>

<decisions>
## Implementation Decisions

### Locked by the user on 2026-07-18 (AskUserQuestion)

- **D-01: Realistic shaped mocks, NOT empty 200s.** Every endpoint returns a correctly-typed
  DTO populated with realistic fake data whose field names and types match
  `initial-db-structure.sql` exactly.
  *Why:* the user's original request said "won't return data but will return 200". That was
  reconsidered and rejected — an empty 200 does not let a UI developer bind fields, render
  lists, or build components, so the contract would not actually be frozen and a second
  integration pass would be needed later. Shaped mocks cost little extra because the 12
  entities already exist from Phase 1.

- **D-02: No auth in this phase.** No JWT, no session, no guard. `user_id` is passed
  explicitly as a path/query/body parameter wherever it is needed.
  *Why:* user's explicit choice over the alternative (an env-gated dev-login stub issuing a
  real-shaped JWT).
  **ACCEPTED COST, recorded deliberately:** every endpoint signature carrying a `userId`
  parameter WILL change when Phase 3 lands, forcing a real UI re-integration pass at that
  point. The user was shown this trade-off explicitly and chose it. **Do not silently add an
  auth stub** to "help" — that would contradict a deliberate decision.

- **D-03: WebSocket emits a full fake cycle, not just a heartbeat.** On subscribe: a full
  `snapshot`. Then, looping: a `game_event` every ~4s (the heartbeat the user asked for),
  a `question` every ~30s carrying 4 options with `expires_at = now + 5s`, and ~5s later
  its `resolution` (winning option + awarded points).
  *Why:* the 4s heartbeat alone proves the connection but leaves the hero screen —
  prediction card, countdown, points animation — unbuildable until Phase 4. The full cycle
  unblocks it now and freezes the WS-01/WS-02 contract at the same time.

- **D-04: Mock data must be deterministic.** No per-request `Math.random()`. The same request
  returns the same body, so the UI developer sees stable payloads and can write fixtures
  against them. (Time-derived fields like `expires_at` are the deliberate exception.)

- **D-05: Contract frozen here, implementations owned later.** Phase 5 must be able to swap
  real logic in behind these exact DTOs with zero UI rework. Treat the DTO shapes as the
  deliverable, the mock bodies as scaffolding.

### Locked by the user on 2026-07-18 (post-research)

- **D-06: CORS origin — UI on 3001, backend stays on 3000.** Introduce a `WEB_APP_ORIGIN` env
  var defaulting to `http://localhost:3001`, validated fail-fast through the existing `AppConfig`
  singleton pattern (never a bare `process.env` read). Applied to BOTH `app.enableCors()` and the
  socket.io gateway's own CORS config — in NestJS 11 these are separate and configuring only the
  HTTP one silently leaves the WS handshake blocked.
  *Why:* `main.ts` currently does `app.listen(process.env.PORT ?? 3000)` and `next dev` also
  defaults to 3000, so they collide. Next.js auto-increments to 3001 when 3000 is occupied, which
  makes this the arrangement that already happens naturally, and it leaves the backend on the port
  used throughout Phases 1–2.

- **D-07: The WS `snapshot` DOES include a match clock field.** Research found no elapsed-time
  field on the current `GameState` type and recommended omitting it; that recommendation was
  **overruled deliberately**. Omitting it would force Phase 5 to add the field later — a contract
  change, which is precisely what this phase exists to prevent, and it would leave the UI unable
  to build a match clock.
  **Planner instruction:** derive the clock shape from the two-clock module Phase 2 ported
  (`clock.ts`) rather than inventing one. If `clock.ts` cannot support a coherent shape, surface
  that as a blocker instead of guessing — a wrong shape frozen into the contract is worse than an
  escalation.

### Resolved by research (2026-07-18) — previously open

- **Pagination:** seq-cursor (`after_seq` / `limit`) for `/games/:gameId/events`, matching the real
  seq-ordered append-only log; plain limit/offset for `/games` and `/leaderboard`.
- **Fake-cycle vs. real-ingest collision:** a non-issue at runtime today — `IngestModule` has zero
  WS awareness. Mitigation is architectural: a new `src/modules/realtime/` module with **zero
  imports from ingest**, so Phase 5 can delete it wholesale.
- **Field casing:** entities stay camelCase (unchanged Phase 1 convention); DTOs declare properties
  literally in snake_case to match `initial-db-structure.sql`. Verified lint-safe — no camelCase
  ESLint rule is configured.
- **Timer cleanup:** `SchedulerRegistry` + `OnModuleDestroy` + `.unref()`. Naive `setInterval` will
  worsen the already-documented Jest open-handles problem
  (`.planning/todos/pending/stream-abort-unhandled-rejection-and-e2e-open-handles.md`).
- **New pitfall:** `squad.id` is `@PrimaryColumn`, NOT `@PrimaryGeneratedColumn` — it has no DB
  default. Squad creation must supply an id explicitly.

### Endpoint additions agreed beyond the original `api-mockup.md` list

The user reviewed and approved all of these:

| Addition | Rationale |
|---|---|
| `game_question_option` children embedded in the `game_question` response (`id`, `outcome_key`, `base_gain`, `display_order`) | The prediction card is the hero screen and is unrenderable without the 4 LOCKED options (base_gain 5/7/15/100). |
| `user_game` create ("join game") | GAME-03. The original list read games *by* `user_id` via `user_game` but nothing created that row. |
| `user_game_answer` get (by user + game) | Needed to render "you picked X → +15 pts" and restore answered state after a refresh. |
| `game_question_outcome` list | The 4 static reference rows (fizzles/danger/shot/goal + `ladder_position`) so the UI labels outcomes from the API instead of hardcoding. |
| `GET /leaderboard` | LDRB-01 — already a committed requirement and present on the mockup. |
| `game` get by id | The live-game screen needs single-game detail; the original list had only all / by-status / by-user. |
| WS `snapshot` on subscribe | WS-01. The heartbeat covers push; this freezes the other half of the contract at no extra cost. |
| `PATCH` user (handle, image) | **Added at user request in a follow-up.** Note this overrides the 2026-07-17 scope decision that placed "profile updates" on the CUT list — a deliberate override, recorded here so it does not later read as scope creep. |

**Explicitly out of scope:** squad update/delete, real auth, real resolution logic.

### Proposed route map (NOT yet locked — planning to confirm)

Field shapes are locked to `initial-db-structure.sql`; these paths are a starting proposal.

```
GET    /users?walletAddress=|handle=|squadId=    list/filter (squadId = teammates)
GET    /users/:userId
POST   /users                                    create (wallet sign-in bypassed)
PATCH  /users/:userId                            handle, image
GET    /users/:userId/score-profile

POST   /squads
GET    /squads/:squadId
GET    /squads?participantId=<userId>
POST   /squads/:squadId/participants
GET    /squads/:squadId/participants
GET    /squads/:squadId/score-profile

GET    /games?status=|userId=                    paginated
GET    /games/:gameId
GET    /games/:gameId/events                     paginated
GET    /games/:gameId/questions?state=           options[] embedded
POST   /games/:gameId/join                       { userId, squadId? }

GET    /question-outcomes                        4 static rows
POST   /answers                                  { userId, gameQuestionId, selectedOptionId }
GET    /answers?userId=&gameId=
GET    /leaderboard?limit=
```

**Schema note:** `user_score_profile` / `squad_score_profile` have `varchar` PKs that
`user.score_profile` / `squad_participant.score_profile` point *at* — the FK direction is
reversed from the intuitive reading. "Get profile by user id" therefore means "get the
profile this user references". Harmless for mocks; it will matter in Phase 5.
</decisions>

<constraints>
## Constraints

- Swagger UI documents every endpoint (API-01); validation via class-validator DTOs with
  structured 4xx, never 500s for expected rejections (API-02).
- CORS configured for the Next.js UI origin, for both REST and the WS handshake (WS-03).
- Field names/types match `initial-db-structure.sql` exactly — this contract is what Phase 5
  implements for real.
- Point values 5/7/15/100 and the shot ladder are LOCKED project-wide; mock options must use
  them, never invented numbers.
- Transport is REST + socket.io only (GraphQL rejected project-wide).
- **Timeline note:** the project brief set feature freeze for the evening of 2026-07-17, with
  2026-07-18 as polish/deploy day. This phase was inserted on 2026-07-18 as a deliberate
  reprioritization to unblock UI integration. Recorded for honesty about the plan-vs-actual
  gap; it is the user's call, not a blocker.
</constraints>

<open_questions>
## Open for planning

All three original open questions are now resolved — see "Resolved by research" above
(pagination → seq-cursor; fake-cycle isolation → a separate `realtime` module with no ingest
imports) and D-06/D-07.

Remaining for the planner to decide:

- Whether mock responses live in a single seeded fixture module or per-controller. A single
  module keeps determinism (D-04) auditable.
- Whether the fake cycle runs per-room on demand or as one global timer. Per-room is more
  faithful to what Phase 5 will do; a global timer is cheaper. Either way the timer-cleanup
  contract above is mandatory.
</open_questions>

<risks>
## Known risks carried into planning

- **Five new packages must be installed** (`@nestjs/websockets`, `@nestjs/platform-socket.io`,
  `socket.io`, `socket.io-client`, `@nestjs/swagger`) — none are currently in `package.json`.
  Research verified versions live via `npm view` and reported the legitimacy check as
  `OK`/`SUS`, where SUS is a "too-new" false positive (same release cohort as the already-pinned
  `@nestjs/core@11.1.28`). **The plan must include a `checkpoint:human-verify` before install** —
  do not let an executor install unreviewed packages unattended.
- **Jest open handles.** The suite already has a documented teardown problem. Any new timer or
  gateway that does not honor the cleanup contract above turns a warning into a hang.
- **Regression surface.** 148 unit + 2 e2e tests must stay green; `src/modules/ingest/**` is
  off-limits.
</risks>
