## Gaps Summary

**One genuine, live-demonstrated gap, tied to a single root cause.**

`RealtimeGateway`'s `@WebSocketGateway({ cors: { origin: process.env.WEB_APP_ORIGIN, credentials:
false } })` only controls the `Access-Control-Allow-Origin` response header value — it is not, by
itself, an access-control mechanism for the WebSocket handshake. Live testing (both a real
`socket.io-client` and a raw `curl` against the engine.io polling endpoint) confirms a connection
from a non-configured `Origin` (`http://evil.example.com`) completes the handshake successfully and
receives the full fake cycle (snapshot, heartbeat) exactly like a legitimate client. This directly
contradicts:

1. An explicit must-have truth recorded in `02.1-04-PLAN.md`'s own frontmatter ("The socket.io
   handshake is rejected for an origin other than the configured WEB_APP_ORIGIN...").
2. A direct factual claim in the shipped `docs/WS-CONTRACT.md` ("the socket.io handshake only
   succeeds from the origin configured...").
3. The intent of threat-model entry T-02.1-19 ("Information Disclosure... mitigate... Acceptance
   criterion greps for the wildcard form and requires zero matches") — the mitigation's own
   acceptance check was a shallow string-absence grep, not a behavioral test, so the actual
   security property was never exercised anywhere in the phase's test suite and shipped unverified.

**Why this was missed:** every automated gate this phase ran (build, 186 unit tests, 40 e2e tests,
`--detectOpenHandles`, the plan's own greps) is silent on this specific behavior. The one e2e spec
that connects a live socket.io client (`test/realtime.e2e-spec.ts`) only exercises the *happy* path
(connecting from the *correct* origin) — it never asserts what happens from a *wrong* one. This is
exactly the class of gap goal-backward verification is meant to catch: an artifact (the `cors`
option) is present and superficially "not a wildcard," but the actual promised behavior (rejection)
does not hold.

**Practical severity today:** low-to-moderate. Every payload the gateway currently emits is
synthetic fixture data (`is_mock: true` on every message) — Spoofing/unauthenticated-room-join is
already an accepted risk in this same plan's own threat model (T-02.1-22), specifically because no
real data exists behind it yet. No PII or real match state is exposed by this gap as things stand
today. The severity is forward-looking: this is exactly the origin-enforcement control Phase 5 is
supposed to inherit "frozen and proven," and right now it is frozen but not proven — a future
reader (including a future Phase 5 executor) could reasonably assume origin enforcement works
because the code has a `cors` option and the docs say so, when it does not.

**Suggested remediation (not applied by this verifier):** add a handshake-time origin check —
either an `allowRequest` callback on the underlying engine.io server (available via
`@WebSocketGateway`'s options, or by configuring the HTTP adapter) that compares
`req.headers.origin` against the configured `WEB_APP_ORIGIN` and refuses the upgrade when it does
not match, or an equivalent guard in `handleConnection`/first message that disconnects a
mismatched-origin socket immediately. Pair the fix with a negative-path e2e assertion in
`test/realtime.e2e-spec.ts` (or a new spec) so this behavior is proven going forward, and correct
`docs/WS-CONTRACT.md`'s claim to match whichever way it is resolved.

This looks like a genuine implementation gap rather than an intentional deviation — there is no
alternative mechanism anywhere in the codebase that achieves the same intent, so no override is
suggested. If the team judges this an acceptable, deliberate risk for a mock-only phase (consistent
with the already-accepted D-02/T-02.1-22 posture), that is a legitimate call, but it should be
recorded as an explicit accepted-risk decision (an override in this file's frontmatter, or an
update to the threat model) rather than left as a silent gap between what the docs/plan claim and
what the code does.

Everything else in this phase — the 20-route REST surface, the Swagger/OpenAPI document, the
class-validator 4xx behavior, the LOCKED 5/7/15/100 ladder, the deterministic fixtures, the full WS
fake cycle's snapshot/heartbeat timing, and the zero-regression guarantee on the Phase 2 ingest
pipeline — was independently re-verified against the live, running application in this session and
holds exactly as SUMMARY.md and COVERAGE.md describe.
