# GutCall WebSocket Contract

**Phase:** 02.1 — Placeholder API Surface & Fake Realtime Contract
**Status:** Frozen contract, mock implementation. Every payload documented here is
generated by a synthetic timer this phase and is **not derived from a real match
feed** — see "This Is a Mock" below before you build against it expecting live data.

Swagger/OpenAPI has no native support for describing WebSocket (socket.io) events,
so this document plus the `@ApiExtraModels`-registered DTO classes (wired into
Swagger's schema section by plan 02.1-05) are, together, the mechanism that makes
this contract discoverable. Every field name and type below is final for Phase 5 —
implementations change, shapes do not (D-05).

## Connection

- **URL:** the same origin/port the REST API is served from (`http://localhost:3000`
  in local development — see `apps/gutcallfun-core/.env.example`'s `PORT`). socket.io
  negotiates its own path (`/socket.io/`) automatically; no extra configuration is
  required client-side beyond pointing at the base URL.
- **CORS:** the gateway sets `Access-Control-Allow-Origin` from the backend's
  `WEB_APP_ORIGIN` environment variable (`http://localhost:3001` locally). This is
  configured **separately** from the REST API's CORS policy (D-06) — the gateway has
  its own `cors` option, and in NestJS 11 configuring only `app.enableCors()` leaves
  the gateway without its own policy. If your client gets a handshake-level CORS
  error on the polling transport while REST calls succeed, this is the first thing
  to check.

  > ⚠️ **Origin is NOT enforced in Phase 02.1 — do not treat this as an access
  > control.** The `cors.origin` option only sets a response *header*; it installs no
  > handshake guard. There is no `allowRequest` hook. CORS does not apply to the
  > WebSocket upgrade at all — it covers only socket.io's *polling* transport (an
  > XHR). Any client that connects with `transports: ['websocket']`, **including a
  > browser page served from any origin**, completes the handshake and receives live
  > data. This was live-verified during Phase 02.1 verification via both a
  > `socket.io-client` and a raw `curl`, each presenting a foreign `Origin`.
  >
  > Impact is accepted for now because this phase serves only deterministic mock
  > fixtures — no auth, no user data, no wallet state. **This becomes a real
  > vulnerability the moment the gateway serves per-user state.** Phase 5 must add a
  > server-side origin check before shipping anything user-scoped over this socket.
  > Tracked at `.planning/todos/pending/ws-handshake-origin-not-enforced.md`.

- **Auth:** none. Per D-02, this phase ships no authentication anywhere — any
  client can subscribe to any `game_id`'s room. This is an accepted, deliberate gap
  (T-02.1-22) that Phase 3 closes.

- **Local dev port note:** the backend runs on `PORT=3000` and expects the UI at
  `WEB_APP_ORIGIN=http://localhost:3001`. `apps/gutcallfun-ui`'s `dev` script is a bare
  `next dev`, which defaults to port **3000** — the backend's port. Start the UI with
  `next dev -p 3001` (or start the backend first so Next.js auto-increments onto 3001),
  otherwise the UI ends up on an origin the backend does not advertise.

## Client → Server Events

### `subscribe`

Join the room for a game and receive its full fake cycle. Emitting `subscribe` for
a `game_id` you are already subscribed to is a no-op — it does not restart or
double the cycle.

**Payload** (`SubscribeDto`):

| Field     | Type    | Notes                        |
|-----------|---------|-------------------------------|
| `game_id` | integer | The game to join the room for |

### `unsubscribe`

Leave the room for a game. If you were the last subscriber remaining in that room,
its fake cycle stops immediately (no more `game_event`/`question`/`resolution`
emissions for that `game_id` until someone subscribes again).

**Payload** (`SubscribeDto`): identical shape to `subscribe`.

## Server → Client Events

All five events below are documented in Swagger's schema section under the DTO
class name listed — look there for the full field list, types, and per-field
descriptions; this table is a quick index, not the source of truth.

| Event | Cadence | DTO class | One-line description |
|-------|---------|-----------|------------------------|
| `snapshot` | once, immediately on `subscribe` | `SnapshotDto` | Full current game state — score, match clock, possession stage, and the currently open question (or `null`) |
| `game_event` | every ~4s while a room has at least one subscriber | `GameEventMessageDto` | A heartbeat event proving the connection is alive and the cycle is running |
| `question` | every ~30s | `QuestionMessageDto` | A new prediction window opens, carrying exactly four options (`base_gain` 5/7/15/100, `display_order` 1-4) |
| `resolution` | ~5s after the `question` it resolves | `ResolutionMessageDto` | The winning option and awarded points for a specific `game_question_id` |
| `void` | **never emitted this phase** | `VoidMessageDto` | Shape frozen now so Phase 4's real void conditions (suspend/disconnect/seq-gap/restart-hole) do not require a contract change later |

### `snapshot` (`SnapshotDto`)

Emitted synchronously right after your `subscribe` is processed — before the fake
cycle has had a chance to fire its first `question`. `active_question` is
therefore always `null` on the very first snapshot you receive; the key is always
present, never omitted, and never an empty object. `clock` (`MatchClockDto`)
carries the D-07 match clock: `current_status_id`, `last_feed_ts`,
`period_started_feed_ts`, and `elapsed_ms` (an integer millisecond count — never a
float, never a preformatted string like `"63:12"`; formatting is a UI concern).

### `game_event` (`GameEventMessageDto`)

A lightweight heartbeat mirroring the real `game_event` log's shape (minus the raw,
unbounded feed body — fetch that separately via `GET /games/:game_id/events` if you
need it). `seq` increments once per emission for the room.

### `question` (`QuestionMessageDto`)

Reuses the exact same `QuestionResponseDto` shape the REST `GET
/games/:game_id/questions` route returns, so the two surfaces of a question can
never drift. Always carries exactly four options in `options[]`, whose
`base_gain` values are the LOCKED, calibrated 5/7/15/100 ladder
(fizzles/danger/shot/goal) and whose `display_order` runs 1-4. `expires_at` is
approximately 5 seconds after emission.

### `resolution` (`ResolutionMessageDto`)

Emitted ~5 seconds after its correlated `question`, carrying the same
`game_question_id`. `resolved_option_id` is always one of the four option ids the
question carried; `awarded_points` is that option's own frozen `base_gain`.

### `void` (`VoidMessageDto`)

**Frozen but never emitted in this phase.** Phase 4 owns the real void
conditions — suspend, disconnect, seq-gap, and restart-hole. This shape exists now
purely so that landing real void logic later is a behavior change, not a wire
contract change.

## This Is a Mock

Every message this gateway emits carries `is_mock: true`. There is no persistence,
no real match state, and no connection whatsoever to the Phase 2 TxLINE ingest
pipeline behind any of it — `src/modules/realtime/` imports nothing from
`src/modules/ingest/` or `src/models/`, by design, so this entire module can be
deleted wholesale once Phase 5 wires the real state machine into the same event
names and payload shapes. Do not report a bug against "a match" based on data from
this cycle — there is no match; it is a timer.

## One Full Cycle, Timed

```
t=0s     client emits `subscribe` { game_id }
t=0s     server emits `snapshot`                     (active_question: null)
t=4s     server emits `game_event`                    (heartbeat)
t=8s     server emits `game_event`                    (heartbeat)
t=12s    server emits `game_event`                    (heartbeat)
  ...    (game_event repeats every ~4s the whole time a room has a subscriber)
t=30s    server emits `question`   { id: Q1, expires_at: t=35s, options: [...] }
t=35s    server emits `resolution` { game_question_id: Q1, resolved_option_id, awarded_points }
t=60s    server emits `question`   { id: Q2, expires_at: t=65s, options: [...] }
t=65s    server emits `resolution` { game_question_id: Q2, ... }
  ...    (question/resolution repeats every ~30s, each resolution 5s after its question)
```

The `question`/`resolution` interval (30s) and the `game_event` heartbeat interval
(4s) run independently and concurrently for the lifetime of a room — they are not
sequenced against each other, only against themselves.

## Room Semantics

Rooms are named `game:{game_id}` (e.g. `game:3`). A room's fake cycle starts on the
first `subscribe` for that `game_id` and stops when the last subscribed client
either emits `unsubscribe` or disconnects — subscribing twice from the same client,
or having two clients subscribed to the same room, never doubles the event rate:
one shared cycle serves the whole room.
